## 笔记：Codex 文档机制

### 1. String/StringBuffer/StringBuilder 区别

String是final修饰的字符数组，每次拼接都会创建新对象，适合少量字符串操作。然后，StringBuffer和StringBuilder都继承自AbstractStringBuilder，底层是可变字符数组。区别在于：StringBuffer的方法用`synchronized`修饰，所以线程安全但慢；StringBuilder没有锁，单线程下最快。因此，**单线程拼接优先用StringBuilder**，多线程共享场景用StringBuffer。

**案例：**

之前在做日志拼接时，循环内用String的`+=`导致频繁GC，改成StringBuilder后性能提升了5倍。

### 2. 反射机制及主要用到的方法

**结论式开场：**

反射是**运行时获取类的信息并动态操作**的机制，核心类是`Class`、`Method`、`Field`、`Constructor`。

**主体：**首先，获取Class对象的三种方式：`Class.forName()`、`对象.getClass()`、`类名.class`。然后，主要方法：`getDeclaredMethods()`获取所有方法，`getDeclaredFields()`获取所有字段，`setAccessible(true)`可以访问私有成员。其次，动态创建对象：`clazz.newInstance()`或构造器的`newInstance()`，调用方法用`method.invoke()`。因此，反射是框架（Spring、MyBatis）的底层基础，但会牺牲性能和安全。**案例：**

写通用Excel导出时，我通过反射遍历对象的字段来动态生成表头，避免了为每个VO写重复代码。

### 3. JVM 内存结构

**结论式开场：**

JVM内存分为**线程共享**的**堆**和**方法区**，以及**线程私有**的**程序计数器**、**虚拟机栈**和**本地方法栈**。

**主体：**首先，**堆**存放所有对象实例和数组，是GC主要管理区域，可细分为新生代和老年代。然后，**方法区**（JDK1.8后为元空间）存放类信息、常量、静态变量。其次，线程私有的部分：**程序计数器**记录当前线程执行的字节码行号；**虚拟机栈**每个方法执行时创建栈帧，存局部变量表、操作数栈等；**本地方法栈**服务native方法。因此，理解内存结构是排查OOM和性能问题的前提。

### 4. == 与 equals 区别

**结论式开场：**

`==`比较的是**内存地址**（基本类型比较值），`equals`是方法，默认也是比较地址，但常被重写为**比较内容**。

**主体：**

首先，对于基本类型，`==`比较数值是否相等，比如`int a=1; int b=1; a==b`为true。对于引用类型，`==`比较两个引用是否指向同一个对象。然后，`equals`是Object的方法，默认实现就是`==`。但是，String、Integer等类重写了`equals`，比较的是对象的实际内容。因此，自定义类如果要实现内容比较，必须重写`equals`和`hashCode`。**案例：**

之前遇到过bug：两个用户对象属性完全一样，但`user1 == user2`返回false，后来改用`Objects.equals()`才正确。

### 5. 接口和抽象类的区别

**结论式开场：**

核心区别在于**多继承支持、状态存储和构造方法**：接口支持多实现，无状态（静态常量除外），Java8后可带默认实现；抽象类单继承，可有成员变量和构造方法。

**主体：**首先，**语法层面**：抽象类用`abstract`修饰，可以有抽象方法和具体方法，可以有成员变量和构造方法；接口用`interface`修饰，方法默认public abstract，变量默认public static final。然后，**设计层面**：抽象类表达的是"is-a"关系（如`Animal`），接口表达的是"can-do"能力（如`Runnable`）。最后，Java8后接口可以写`default`和`static`方法，但不能有状态。

**补充：**

选型原则：行为复用优先抽象类，能力契约优先接口。实际项目中常用"抽象类+接口"组合设计。

### 6. 重写（override）和重载（overload）的区别

**结论式开场：**

重载是**编译时多态**，同一个类中方法名相同、参数列表不同；重写是**运行时多态**，子类重新定义父类方法，方法签名必须相同。

**主体：**

首先，**重载**：发生在同一个类中，方法名相同，参数个数、类型或顺序不同，与返回值和修饰符无关。编译时根据参数决定调用哪个方法。然后，**重写**：发生在父子类或接口实现类中，方法名、参数列表、返回类型（协变返回）必须相同，访问权限不能更严格，不能抛出更宽泛的异常。运行时根据实际对象类型决定调用。因此，重载是"静态绑定"，重写是"动态绑定"。**案例：**

Spring的`ApplicationContext.getBean()`有多种重载版本（按类型、按名字、按类型+名字），就是典型的重载应用。

### 7. sleep 和 wait 的区别

**结论式开场：**

sleep是**Thread的静态方法**，不释放锁；wait是**Object的实例方法**，必须配合synchronized使用，会释放锁。

**主体：**首先，**所属不同**：sleep属于Thread，wait属于Object。然后，**锁行为不同**：sleep期间当前线程不释放任何锁；wait会让当前线程释放持有的锁，进入等待队列。其次，**唤醒方式不同**：sleep到时间自动唤醒或被interrupt；wait必须被notify/notifyAll唤醒或超时。最后，**使用范围**：sleep可以在任何地方调用；wait必须在synchronized块/方法内。

**补充：**

面试经典陷阱："sleep之后会释放CPU吗？"会的，释放CPU但不释放锁。

### 8. String 类的常用方法

**结论式开场：**

String常用方法按功能分四类：**判断比较**（equals、isEmpty）、**转换截取**（substring、toCharArray）、**查找替换**（indexOf、replace）、**分割拼接**（split、join）。

**主体：**

首先，**判断类**：`equals`比较内容，`equalsIgnoreCase`忽略大小写，`startsWith/endsWith`判断前缀后缀，`isEmpty/isBlank`判空。然后，**截取转换**：`substring(begin,end)`，`toLowerCase/toUpperCase`，`toCharArray`转字符数组，`trim`去首尾空格。其次，**查找替换**：`indexOf/lastIndexOf`查找位置，`replace/replaceAll`替换，`contains`判断包含。最后，**分割拼接**：`split`正则分割，`join`拼接，`concat`连接。

### 9. 类加载器加载过程

**结论式开场：**

类加载分为**加载→验证→准备→解析→初始化**五个阶段，其中解析可能晚于初始化（动态绑定）。

**主体：**

首先，**加载**：通过全类名获取二进制字节流，转化为方法区的数据结构，生成Class对象。然后，**验证**：校验字节流格式、语义、符号引用合法性。其次，**准备**：为静态变量分配内存并赋零值（不是代码中的初始值）。然后，**解析**：将符号引用替换为直接引用（类或接口、字段、方法）。最后，**初始化**：执行静态代码块和静态变量显式赋值，父类先初始化。

### 10. 双亲委派机制

**结论式开场：**

双亲委派是**类加载器收到加载请求时先委派给父加载器**，父加载器无法加载才自己加载，核心目的是**保证核心类库安全**。

**主体：**

首先，类加载器有层级：启动类加载器（Bootstrap）→ 扩展类加载器（Extension）→ 应用类加载器（Application）→ 自定义类加载器。然后，工作流程：当应用类加载器收到加载请求，先询问父加载器（扩展类）"你能加载吗？"，扩展类再向上问启动类。如果父加载器找不到，子加载器才尝试自己加载。因此，java.lang.String永远由启动类加载器加载，不会被恶意篡改。

**补充：**

Tomcat打破双亲委派的例子：每个Web应用有自己的WebappClassLoader，先自己加载Web应用的类，实现隔离。

### 11. JVM 的 GC 垃圾回收机制

**结论式开场：**

GC机制是**自动内存管理**，核心解决三个问题：**哪些内存可回收（可达性分析）、什么时候回收、怎么回收（垃圾回收算法）**。

**主体：**

首先，**判断对象存活**：采用可达性分析法，从GC Roots出发，不可达对象被标记。GC Roots包括栈帧局部变量、静态变量、JNI引用等。然后，**回收算法**：标记-清除（有碎片）、复制算法（新生代，对象存活率低）、标记-整理（老年代，存活率高）、分代收集（新生代+老年代配不同算法）。其次，**回收器**：Serial、Parallel、CMS、G1、ZGC等，G1是JDK9后默认，平衡吞吐量和延迟。

### 12. JVM 如何调优（调优参数）

**结论式开场：**

JVM调优本质是**根据业务特征调整内存分配和GC策略**，核心参数分为**内存大小类**和**GC选型类**。

**主体：**

首先，**内存参数**：`-Xms`初始堆大小、`-Xmx`最大堆大小（通常设为相同，避免扩容抖动）、`-Xmn`新生代大小、`-XX:MetaspaceSize`元空间、`-XX:MaxDirectMemorySize`直接内存。然后，**GC参数**：`-XX:+UseG1GC`选G1回收器，`-XX:MaxGCPauseMillis`设置目标停顿时间，`-XX:+PrintGCDetails`打印GC日志。其次，**调优步骤**：先压测，监控GC次数和耗时；调节-Xmn和SurvivorRatio避免对象过早晋升老年代；优化大对象分配。

**补充：**

一个常见调优：IO密集型应用堆内存可稍小，CPU密集型可稍大。

### 13. 项目是否出现过OOM问题？怎么排查的？可能原因？如何复现一个内存溢出场景？内存溢出和内存泄露的区别？

**结论式开场：**

遇到过OOM，排查流程是**dump堆→MAT分析→定位代码**；内存溢出是"不够用"，内存泄漏是"占着不放"。

**主体：**

首先，**排查**：出现OOM时，用`-XX:+HeapDumpOnOutOfMemoryError`自动dump堆内存，用MAT工具分析，找到最大对象和GC Roots引用链。可能原因：内存泄漏（如监听器未移除）、大对象频繁分配（如读取超大文件）、内存容量不足。然后，**复现场景**：写一个无限循环往List里add对象，加上`-Xmx10m`。其次，**区别**：内存溢出是程序申请内存超过可用量；内存泄漏是已使用内存无法被GC回收，最终累积成溢出。**案例：**

之前遇到Metaspace OOM，排查发现Groovy动态编译类导致类加载器未卸载，加`-XX:MaxMetaspaceSize`限制并升级版本解决。

### 14. JDK1.8 的新特性

**结论式开场：**

JDK1.8核心特性：**Lambda表达式、Stream API、Optional类、新的日期API、接口默认方法、元空间替代永久代**。

**主体：**首先，**Lambda+Stream**：让集合处理函数式编程，如`list.stream().filter(x->x>0).collect()`，写出更易读的代码。然后，**Optional**：优雅解决空指针，`orElseGet`提供默认值。其次，**新日期API**：`LocalDate/LocalDateTime`不可变线程安全，解决老的Date/Calendar混乱问题。**默认方法**：接口可以写`default`实现，增强扩展性而无需修改实现类。最后，**元空间**：从堆移到本地内存，避免永久代OOM。

### 15. Error 和 Exception 的区别

**结论式开场：**

Error是**系统级不可恢复问题**，如OOM、StackOverflow；Exception是**程序级可处理问题**，分为受检异常和运行时异常。

**主体：**

首先，**Error**：JVM内部错误或资源耗尽，程序不应该也不通常能捕获处理，比如`OutOfMemoryError`、`NoClassDefFoundError`。然后，**Exception**：程序运行中的异常条件，又分两类。**受检异常**（Checked）如IOException、SQLException，编译时强制处理或抛出；**非受检异常**（Unchecked/RuntimeException）如NullPointerException、IllegalArgumentException，编译不检查。因此，业务逻辑异常建议用RuntimeException，外部IO/网络用受检异常。

**补充：**

Spring的事务回滚默认只对RuntimeException和Error回滚，受检异常不自动回滚，这是常见坑点。

## 集合

### 1. Java常用的集合、分类、涉及到的接口

**结论式开场：**

Java集合框架分为两大体系：**Collection**（单元素集合）和**Map**（键值对集合），顶层接口分别是`Collection`和`Map`。

**主体：**

首先，**Collection体系**往下分三类：**List**（有序可重复，如ArrayList、LinkedList）、**Set**（无序不可重复，如HashSet、TreeSet）、**Queue**（队列，如ArrayDeque）。然后，**Map体系**存储键值对，主要实现类：HashMap、LinkedHashMap、TreeMap、ConcurrentHashMap。其次，各接口特点：List可以通过索引访问，Set依赖`hashCode`和`equals`去重，Queue支持FIFO操作，Map通过key快速查找value。

**补充：**

另外还有迭代器接口`Iterator`和工具类`Collections`、`Arrays`，提供排序、查找、同步包装等辅助功能。

### 2. HashMap底层原理

**结论式开场：**

HashMap底层是**数组+链表+红黑树**的结构，通过哈希值定位数组索引，冲突时用链地址法解决，链表过长（>8）时转为红黑树优化查询。

**主体：**

首先，**put流程**：计算key的hashCode，再通过高位扰动（`(h = key.hashCode()) ^ (h >>> 16)`）得到hash值；然后`(n-1) & hash`定位数组下标。如果没有元素，直接放入；如果有，判断key是否相等，相等则覆盖，否则插入链表尾部（JDK1.8）。然后，**扩容机制**：当元素数量超过阈值（容量×负载因子0.75），数组扩容为2倍，重新计算每个元素的位置。其次，**链表树化**：当链表长度超过`TREEIFY_THRESHOLD=8`，且数组长度≥64，链表转为红黑树；红黑树退化阈值是6。**get流程**：类似定位，在链表/红黑树中遍历查找。

### 3. HashMap为什么用红黑树不用B树

**结论式开场：**

因为**B树是为磁盘存储设计的多路搜索树**，而HashMap的数据全在内存中，红黑树的**内存占用和插入删除效率**更适合内存场景。

**主体：**

首先，B树每个节点可存储多个key，减少磁盘I/O次数，适合数据库索引这种磁盘读取场景。然后，**内存场景下**，红黑树的节点占用更小（没有存储子节点指针数组的开销），插入删除的旋转操作比B树的节点分裂/合并更轻量。其次，HashMap中每个桶是独立的小规模冲突管理，红黑树在链表长度8~64之间就能提供O(log n)查找，B树的最低阶数都太大了，会浪费内存。因此，红黑树是内存哈希表冲突解决的经典选择。

### 4. HashMap什么时候扩容

**结论式开场：**

HashMap在**put元素后size超过阈值**时扩容，阈值 = 容量 × 负载因子（默认0.75），另外**链表转红黑树时若数组长度小于64也会触发扩容**。

**主体：**

首先，**常规扩容**：每次put后检查`size > threshold`，阈值默认`16 × 0.75 = 12`，达到12就扩容为原来的2倍。然后，**特殊情况**：当链表长度达到8时，会调用`treeifyBin()`方法。但该方法内部会判断数组长度是否小于`MIN*TREEIFY*CAPACITY=64`，如果小于，它会选择扩容而不是树化，因为更小的数组主要是哈希碰撞分布不均匀，扩容重新哈希后能改善分布。因此，扩容时机本质是为了在**空间换时间**。

### 5. HashMap的长度为什么是2的N次方

**结论式开场：**

核心目的是**用位运算`(n-1) & hash`代替取模运算`hash % n`**，效率更高，同时保证分布均匀。

**主体：**

首先，当n是2的幂时，`(n-1)`的二进制是低位全1，比如16-1=15（1111），和hash做`&`运算等价于`hash % 16`，但位运算比取模快10倍以上。然后，**分布均匀**：如果n不是2的幂，低位的1可能不连续，导致哈希碰撞概率增加。其次，扩容时也受益：2倍扩容后，元素要么留在原索引，要么移动到“原索引+旧容量”的位置，只需要重新计算一个bit位，不需要重新哈希。

**补充：**

这就是为什么HashMap要求容量必须是2的幂，即使你传入17，它也会通过`tableSizeFor`方法找到大于等于17的最小2的幂，即32。

### 6. HashMap和HashTable区别

**结论式开场：**

核心区别：**线程安全**（HashTable全表锁，HashMap不安全）、**null支持**（HashMap允许一个null key和多个null value，HashTable不允许）、**性能**（HashMap更快）。

**主体：**

首先，**线程安全**：HashTable所有公共方法都用`synchronized`修饰，是强同步；HashMap无锁，单线程下性能更高。多线程需用`Collections.synchronizedMap`或`ConcurrentHashMap`。然后，**null处理**：HashMap在put null key时，hash值为0，放在数组0号位置；HashTable key为null会抛出NullPointerException。其次，**继承和容量**：HashTable继承Dictionary，默认容量11，扩容2倍+1；HashMap继承AbstractMap，默认容量16，扩容2的幂。最后，**HashTable已废弃**，新代码不建议使用。

### 7. ConcurrentHashMap和HashMap的区别

**结论式开场：**

核心区别是**线程安全性**：ConcurrentHashMap通过分段锁或CAS+synchronized实现高并发线程安全，而HashMap非线程安全。

**主体：**

首先，**线程安全**：HashMap多线程同时put会导致死循环（JDK1.7头插法，1.8修了但仍有数据覆盖问题），ConcurrentHashMap的get和put都是线程安全的。然后，**结构差异**：HashMap允许null key/value，ConcurrentHashMap不允许。其次，**迭代器**：HashMap的迭代器是fast-fail（检测到并发修改立刻抛异常），ConcurrentHashMap的迭代器是弱一致性，允许并发修改，遍历时可能看不到最新元素。因此，**单线程用HashMap，多线程用ConcurrentHashMap**。

### 8. ConcurrentHashMap和HashTable区别，他们如何保证线程安全

**结论式开场：**

ConcurrentHashMap用**分段锁粒度更细**（JDK1.8前是Segment，1.8后是CAS+synchronized锁桶头），HashTable用**全表锁**，两者性能差几十倍。

**主体：**

首先，**HashTable的安全机制**：每个public方法都加`synchronized(this)`，同一时刻只有一个线程能操作整个Map，并发性能极差。然后，**ConcurrentHashMap 1.7**：使用Segment数组，每个Segment相当于一个小HashTable，默认16个Segment支持16个线程同时写。然后，**ConcurrentHashMap 1.8**：取消Segment，直接用`CAS + synchronized`锁桶的头节点。put时，如果桶空，CAS插入；如果有冲突，synchronized锁住链表头或树根，其他桶不受影响。因此，**ConcurrentHashMap的并发度=数组长度**，远高于HashTable。

### 9. ArrayList与LinkedList区别

**结论式开场：**

**ArrayList是数组**，随机访问O(1)，中间插入/删除O(n)；**LinkedList是双向链表**，随机访问O(n)，头尾操作O(1)。

**主体：**

首先，**底层结构**：ArrayList维护一个Object数组，可以快速索引；LinkedList维护Node节点，每个节点指向前后。然后，**性能差异**：遍历元素ArrayList更快（内存连续，CPU缓存友好）；频繁在中间插入删除，理论上LinkedList更快，但实际查找位置也要O(n)，差距并不大。其次，**内存占用**：ArrayList可能浪费尾部空间；LinkedList每个节点额外存储前后指针，每个元素内存占用更大。因此，**绝大多数场景选ArrayList**，只有频繁头尾操作或需要作为双端队列时才用LinkedList。

### 10. 遍历LIST有哪些方式

**结论式开场：**

有**4种**方式：普通for循环、增强for循环、迭代器Iterator、以及Java8的forEach+Lambda。

**主体：**

首先，**普通for**（`for(int i=0;i<list.size();i++)`）：通过索引访问，适合ArrayList，但LinkedList非常慢。然后，**增强for**（`for(Object o: list)`）：语法糖，编译为迭代器，最常用。其次，**迭代器**：可以边遍历边删除（调用`iterator.remove()`），增强for做不到。最后，**Java8 Stream**：`list.forEach(System.out::println)`，代码简洁，还可链式操作（filter/map）。

**补充：**

遍历时删除元素的正确姿势：必须用`Iterator.remove()`或普通for倒序遍历，不能用增强for，会抛出`ConcurrentModificationException`。

### 11. 数组(Array)和列表(ArrayList)区别

**结论式开场：**

Array是**定长、基础类型支持**，ArrayList是**动态扩容、只能存储对象**，本质是Array的封装。

**主体：**

首先，**长度**：Array声明后长度固定，不能改变；ArrayList自动扩容，当容量不足时创建新数组并拷贝旧数据。然后，**类型**：Array可以存储基本类型（int、char等）和对象；ArrayList只能存储对象，存储基本类型需要包装类，有装箱开销。其次，**方法**：ArrayList提供丰富的API（`add`、`remove`、`contains`等），Array只有`length`属性和下标访问。因此，**数据量固定且是基本类型时用Array**，否则用ArrayList更灵活。

### 12. 线程安全的集合类和有序的集合类

**结论式开场：**

**线程安全集合**位于`java.util.concurrent`包，如`ConcurrentHashMap`、`CopyOnWriteArrayList`、`BlockingQueue`；**有序集合**指保持顺序的集合，如`TreeSet/TreeMap`和`LinkedHashMap/LinkedHashSet`。

**主体：**

首先，**线程安全类**：`ConcurrentHashMap`替代HashTable，`CopyOnWriteArrayList`替代Vector（读写分离，适合读多写少），`ArrayBlockingQueue/LinkedBlockingQueue`用于生产者消费者模式。然后，**有序集合**分两种：一是**自然顺序或Comparator排序**的`TreeMap/TreeSet`（红黑树）；二是**插入顺序**的`LinkedHashMap/LinkedHashSet`（双向链表维护顺序）。其次，`SortedSet/SortedMap`接口也代表有序。因此，线程安全和有序不是互斥的，比如`ConcurrentSkipListMap`就是线程安全+有序（跳表实现）。

## 线程和锁

### 1. 线程的状态

**结论式开场：**

Java线程有6种状态：**NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED**，通过`Thread.getState()`获取。

**主体：**

首先，**NEW**：线程创建但未调用`start()`。然后，**RUNNABLE**：调用`start()`后，包含就绪和运行两种子状态，等待CPU调度。其次，**BLOCKED**：等待进入synchronized块时被阻塞，区别于等待`wait/notify`。**WAITING**：无限期等待其他线程唤醒，如`Object.wait()`、`Thread.join()`、`LockSupport.park()`。**TIMED_WAITING**：有时间限制的等待，如`sleep(1000)`、`wait(1000)`。最后，**TERMINATED**：线程执行完毕或异常退出。

**补充：**

面试常见陷阱：`sleep`是TIMED_WAITING且不释放锁，`wait`是WAITING且释放锁。

### 2. 创建线程的方式

**结论式开场：**

有**4种**：继承Thread类、实现Runnable接口、实现Callable接口（带返回值）、以及通过线程池创建。

**主体：**

首先，**继承Thread**：重写`run()`方法，直接`new MyThread().start()`，但单继承局限性。然后，**实现Runnable**：实现`run()`，传参给`new Thread(runnable)`，更灵活，推荐方式。其次，**Callable+FutureTask**：`call()`方法有返回值可抛异常，通过`FutureTask`包装后提交给线程池执行，`get()`获取结果。最后，**线程池**：用`Executors`工具类或直接`ThreadPoolExecutor`创建，复用线程，减少创建销毁开销。

### 3. 线程池核心参数

**结论式开场：**

线程池核心参数有7个，最关键的是**corePoolSize、maximumPoolSize、keepAliveTime、workQueue、threadFactory、handler**。

**主体：**

首先，**corePoolSize**：核心线程数，即使空闲也会存活（除非设置`allowCoreThreadTimeOut`）。**maximumPoolSize**：最大线程数，队列满后还能创建的线程上限。**keepAliveTime**：非核心线程空闲超时后销毁。**workQueue**：任务等待队列，如`ArrayBlockingQueue`、`LinkedBlockingQueue`。然后，**threadFactory**：创建线程的工厂，可自定义线程名。**handler**：拒绝策略。**unit**：时间单位。

**补充：**

还有一个容易被忽略的：`allowCoreThreadTimeOut`，设置为true可以让核心线程也超时销毁。

### 4. 如何创建线程池

**结论式开场：**

**禁止用`Executors`工具类**创建，直接使用`ThreadPoolExecutor`构造函数，手动指定所有参数。

**主体：**

首先，错误方式：`Executors.newFixedThreadPool`和`newCachedThreadPool`存在隐患。`FixedThreadPool`任务队列无界（`LinkedBlockingQueue`最大Integer.MAX*VALUE），堆积过多会导致OOM。`CachedThreadPool`最大线程数无界（Integer.MAX*VALUE），高并发下会创建太多线程导致系统崩溃。因此，正确方式：`new ThreadPoolExecutor(core, max, keepAlive, TimeUnit.SECONDS, new ArrayBlockingQueue<>(1000), new ThreadPoolExecutor.CallerRunsPolicy())`，根据场景明确每个参数。

### 5. 线程池工作原理

**结论式开场：**

线程池工作流程是：**核心线程 → 任务队列 → 非核心线程 → 拒绝策略**，四步阶梯式处理。

**主体：**

首先，当提交一个任务，如果**当前线程数 < corePoolSize**，直接创建新线程执行。然后，如果已满，任务被放入**workQueue**等待。其次，如果**队列已满**且当前线程数 < maximumPoolSize，创建**非核心线程**处理当前任务。最后，如果线程数已达最大且队列也满，触发**拒绝策略**。非核心线程空闲超过keepAliveTime会被销毁，直到数量降到corePoolSize。**案例：**

之前配置一个线程池：core 4，max 10，队列容量100。压测时200并发，前4个直接执行，接下来100个入队，再进来10个创建非核心线程处理，最后86个触发拒绝策略。

### 6. 线程池大小如何设定

**结论式开场：**

线程池大小取决于任务类型：**CPU密集型**建议`N+1`，**IO密集型**建议`2N~4N`（N为CPU核心数）。

**主体：**首先，**CPU密集型**任务（如复杂计算）：线程数不宜超过CPU核心数，否则上下文切换开销大于并行收益，经验公式`N+1`。然后，**IO密集型**任务（如DB查询、HTTP调用）：线程会频繁阻塞，可以设置更多线程来利用等待时间，经验公式`2N`，高延迟场景可到`4N`。其次，更精确的方法：压测观察CPU利用率，目标是让CPU达到80%~90%，通过调整线程池大小找到最佳点。因此，没有万能公式，需要实测。

**补充：**

一个公式参考：`线程数 = N（CPU核心数） × （1 + 平均等待时间 / 平均计算时间）`。

### 7. 线程池的拒绝策略有哪些

**结论式开场：**

有**4种**内置策略：`AbortPolicy`（默认，抛异常）、`CallerRunsPolicy`（调用者线程执行）、`DiscardPolicy`（静默丢弃）、`DiscardOldestPolicy`（丢弃队列头，重试提交）。

**主体：**

首先，**AbortPolicy**：直接抛出`RejectedExecutionException`，适合必须感知拒绝的场景。**CallerRunsPolicy**：让提交任务的线程自己去执行，既能减缓任务提交速度，又不会丢失任务，适合削峰场景。**DiscardPolicy**：直接丢弃，静默处理。**DiscardOldestPolicy**：丢弃队列里等待最久的任务，然后重新提交当前任务。因此，**秒杀系统常用CallerRunsPolicy**，关键任务建议自定义策略（如记录日志+落库）。

### 8. 线程池是一个服务一个还是整体使用一个，为什么

**结论式开场：**

**按隔离原则**：不同业务场景应该用不同线程池，而不是全局共用一个。

**主体：**

首先，如果一个线程池服务所有业务，慢任务会占满线程池，快任务也会被阻塞，导致**雪崩效应**。然后，应该按业务隔离：核心交易用一个线程池，非核心报表用另一个，异步通知用第三个。其次，具体大小也可以差异化：核心业务线程数保守，队列适当小；非核心可以宽松。因此，常见的做法是**一个服务内定义多个线程池**，比如`orderExecutor`、`smsExecutor`，并通过Spring容器管理。**案例：**

之前一个服务里，导出功能用了全局线程池，导出大文件慢导致其他正常请求也被阻塞，后来拆分成独立的导出线程池，问题消失。

### 9. synchronized 和 lock 的区别

**结论式开场：**

`synchronized`是**JVM层面**的关键字，自动释放锁；`Lock`是**API层面**的接口，需要手动`unlock()`，功能更灵活。

**主体：**首先，**使用方式**：synchronized用在方法或代码块，自动加锁释放；Lock需要`lock()`和`unlock()`，并且`unlock()`必须在finally块中。然后，**灵活性**：Lock支持尝试非阻塞获取锁（`tryLock()`）、可中断获取（`lockInterruptibly()`）、超时获取。其次，**性能**：现代JDK中两者性能差异不大，synchronized有锁升级优化。**公平性**：synchronized是非公平锁；Lock可以构造公平锁。因此，**简单场景用synchronized**，需要高级特性（尝试锁、超时）用ReentrantLock。

### 10. synchronized 的锁种类

**结论式开场：**

synchronized锁有**三种**应用方式：**实例方法锁**（锁当前实例）、**静态方法锁**（锁Class对象）、**代码块锁**（锁指定对象）。

**主体：**

首先，**实例方法**：`public synchronized void method()`，锁住的是`this`对象，不同实例不互斥。然后，**静态方法**：`public static synchronized void method()`，锁住的是Class对象，全局唯一，所有实例共享。其次，**代码块**：`synchronized(obj) {...}`，可以锁任意对象，粒度最细。另外，JVM还做了**锁升级**优化：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，根据竞争激烈程度自动升级。

### 11. 什么情况下会产生死锁，如何解决

**结论式开场：**

死锁产生的**四个必要条件**：互斥、持有并等待、不可剥夺、循环等待。解决办法：**破坏任意一个条件**。

**主体：**

首先，典型场景：线程A持有锁1等待锁2，线程B持有锁2等待锁1，形成循环等待。然后，**预防方法**：1）破坏持有并等待：一次性申请所有资源；2）破坏不可剥夺：使用`Lock.tryLock()`设置超时；3）破坏循环等待：规定全局统一的加锁顺序，比如先锁A对象再锁B对象。其次，**排查方式**：用`jstack`查看线程堆栈，搜索“deadlock”关键字，工具会直接显示死锁线程。因此，代码规范上，避免嵌套锁，如果必须用锁，统一加锁顺序。**案例：**

之前转账系统，转A到B先锁A，转B到A先锁B，高并发下死锁。后来统一按用户ID的哈希值排序加锁，死锁消失。

### 12. ThreadLocal 是一个什么样的技术

**结论式开场：**

ThreadLocal是**线程局部变量**，每个线程都有自己独立的变量副本，线程之间互不干扰，常用于**传递上下文**和**避免参数透传**。

**主体：**首先，原理：每个`Thread`对象内部维护一个`ThreadLocalMap`，key是ThreadLocal实例的弱引用，value是存储的值。当你调用`set(T)`，实际是往当前线程的Map里放值。然后，**典型应用**：Spring事务管理中的`ConnectionHolder`、Web请求中的用户上下文（`RequestContextHolder`）、日期格式化的`SimpleDateFormat`（线程不安全，用ThreadLocal隔离）。其次，**注意内存泄漏**：key是弱引用，value是强引用。线程池场景下，线程复用时`remove()`必须调用，避免value无法被回收。**案例：**

我之前用ThreadLocal存储当前登录用户信息，避免在每个方法传参，代码清爽很多。但记得finally中`remove()`。

### 13. 悲观锁和乐观锁的区别

**结论式开场：**

悲观锁**假设冲突一定会发生**，先加锁阻塞别人；乐观锁**假设冲突很少发生**，更新时检查版本号，失败则重试。

**主体：**首先，**悲观锁**：代表有synchronized、ReentrantLock、数据库`select for update`。每次读写都加锁，适合写多读少、冲突高的场景。然后，**乐观锁**：代表有CAS（原子类）、数据库版本号（`update set version=version+1 where id=xx and version=oldVersion`）。更新时检查数据是否被改过，也没改就提交；被改了就重试或报错。适合读多写少、冲突低的场景。因此，**性能上乐观锁通常更好**，但会有ABA问题（CAS版本加时间戳解决）。

**补充：**

AtomicInteger的`incrementAndGet`就是乐观锁+CAS，底层调用`Unsafe.compareAndSwapInt`，失败自旋重试。

### 1. TCP和UDP的区别

**结论式开场：**

TCP是**面向连接、可靠、基于字节流**的传输协议；UDP是**无连接、不可靠、基于数据报**的传输协议。TCP更可靠但慢，UDP快但会丢包。

**主体：**

首先，**连接性**：TCP需要三次握手建立连接，四次挥手断开；UDP不需要，直接发数据。然后，**可靠性**：TCP有确认重传、流量控制、拥塞控制机制，保证数据顺序和完整性；UDP不保证，数据可能丢失、乱序。其次，**效率**：TCP头部最小20字节，且确认机制开销大；UDP头部固定8字节，无确认，适合实时性要求高的场景。因此，**HTTP、数据库连接用TCP**；**视频直播、DNS、游戏位置同步用UDP**。

### 2. 常见的HTTP响应状态码

**结论式开场：**

状态码分为五类：**1xx（信息）、2xx（成功）、3xx（重定向）、4xx（客户端错误）、5xx（服务端错误）**。核心记10个左右。

**主体：**

首先，**2xx成功**：200（OK，标准响应）、201（Created，创建成功）、204（No Content，删除成功无返回）。然后，**3xx重定向**：301（永久重定向，换域名）、302（临时重定向）、304（Not Modified，未修改，走缓存）。其次，**4xx客户端错误**：400（Bad Request，参数错误）、401（Unauthorized，未认证）、403（Forbidden，无权限）、404（Not Found）、429（Too Many Requests，限流）。最后，**5xx服务端错误**：500（Internal Server Error，通用服务异常）、502（Bad Gateway，网关错误）、503（Service Unavailable，服务过载或停机）、504（Gateway Timeout，网关超时）。

### 3. GET和POST的区别

**结论式开场：**

核心区别：GET是**幂等、参数在URL、长度有限、可缓存**；POST是**非幂等、参数在Body、无长度限制、不缓存**。但底层都是TCP。

**主体：**

首先，**语义和幂等性**：GET用于获取数据，多次请求结果相同，是幂等的；POST用于提交数据，多次请求可能产生多个资源，非幂等。然后，**参数位置**：GET参数拼在URL的`?`后面，有长度限制（浏览器2KB~8KB）；POST参数在请求体，理论上无限。其次，**安全性和缓存**：GET请求会被浏览器缓存、保存在历史记录、可被收藏；POST不会。因此，**查询用GET，修改/创建用POST**。注意：真正安全靠HTTPS，GET的URL也会在服务器日志中可见，敏感信息不要用GET。

### 4. Cookie和Session的区别

**结论式开场：**

Cookie是**客户端存储**（浏览器），Session是**服务端存储**。Cookie有大小限制（4KB），Session更安全但占用服务器内存。

**主体：**

首先，**存储位置**：Cookie保存在浏览器，随HTTP请求自动发送；Session保存在服务器内存（或Redis），只给客户端一个SessionId（存在Cookie里）。然后，**安全性**：Cookie可被篡改和拦截，敏感信息不安全；SessionId即便被获取，会话信息仍在服务端，更安全。其次，**生命周期**：Cookie可设置过期时间，持久存储；Session依赖会话，默认30分钟无活动失效。因此，**记住登录状态用Cookie存加密用户标识**；**登录态校验用Session**。实际项目中，分布式Session常存Redis，不依赖单机内存。

### 5. 过滤器和拦截器的区别

**结论式开场：**

过滤器（Filter）是**Servlet规范**，依赖容器，作用于**请求进入Servlet前后**；拦截器（Interceptor）是**Spring MVC规范**，作用于**Controller方法前后**，粒度更细。

**主体：**

首先，**依赖范围**：Filter是JavaEE标准，任何Web容器都支持，可以处理所有Web资源（包括静态资源）；Interceptor是Spring提供的，只能处理Controller请求。然后，**执行时机**：Filter在Servlet处理之前，Interceptor在请求进入Controller之前、执行后、视图渲染后等多个切入点。其次，**核心能力**：Filter可以修改请求和响应流，适合做字符编码、日志记录、权限校验；Interceptor可以获取Spring的Bean，可以访问HandlerMethod信息，适合做更精细的权限控制、接口耗时统计。因此，**需要框架无关的能力用Filter**，**需要Spring特性的用Interceptor**。

## 设计模式

### 1. 单例模式的几种写法

**结论式开场：**

单例模式核心是**保证一个类只有一个实例**，常见写法：饿汉式、懒汉式（双重检查锁）、静态内部类式、枚举式。**推荐枚举或静态内部类**。

**主体：**

首先，**饿汉式**：类加载时就创建实例，线程安全，但可能提前创建浪费内存。写法：`private static final Singleton INSTANCE = new Singleton();`。然后，**懒汉式（双重检查锁）**：第一次调用时才创建，使用`volatile + synchronized`保证线程安全。适合延迟加载场景。其次，**静态内部类式**：利用类加载机制，外部类加载时内部类不会初始化，调用时才加载，既懒加载又线程安全。写法：内部类持有静态实例。最后，**枚举式**：最简洁，自动支持序列化和防反射攻击，是《Effective Java》推荐的方式。

**补充：**

实际项目中，简单场景用饿汉式；需要延迟加载用静态内部类；涉及序列化或反射安全用枚举。

### 2. Spring 中的设计模式有哪些

**结论式开场：**

Spring大量使用了设计模式，核心的有：**工厂模式**（BeanFactory）、**单例模式**（Bean默认单例）、**代理模式**（AOP）、**模板模式**（JdbcTemplate）、**观察者模式**（ApplicationEvent）。

**主体：**

首先，**工厂模式**：`BeanFactory`和`ApplicationContext`是典型工厂，根据配置创建和管理Bean。然后，**单例模式**：Spring的Bean默认作用域是singleton，容器内只有一个实例。**代理模式**：AOP底层用JDK动态代理或CGLIB，为目标对象生成代理，实现切面增强。其次，**模板模式**：`JdbcTemplate`、`RedisTemplate`等，定义算法骨架，具体步骤由回调实现。**观察者模式**：`ApplicationEvent`和`ApplicationListener`，实现事件驱动编程。最后，还有**适配器模式**（HandlerAdapter）、**装饰器模式**（BeanWrapper）等。

### 3. MyBatis 中有哪些设计模式

**结论式开场：**

MyBatis核心设计模式有：**建造者模式**（SqlSessionFactoryBuilder）、**工厂模式**（SqlSessionFactory）、**代理模式**（Mapper代理）、**模板模式**（BaseExecutor）。

**主体：**

首先，**建造者模式**：`SqlSessionFactoryBuilder`通过`build()`方法，解析配置文件逐步构建复杂的`SqlSessionFactory`。然后，**工厂模式**：`SqlSessionFactory`负责生产`SqlSession`，隔离创建细节。**代理模式**：MyBatis为Mapper接口生成动态代理（JDK代理），调用接口方法时转换为SQL执行。其次，**模板模式**：`BaseExecutor`定义执行器骨架，具体步骤如`doUpdate`、`doQuery`留给子类实现（`SimpleExecutor`、`BatchExecutor`）。还有**装饰器模式**：`CachingExecutor`装饰普通Executor，添加二级缓存功能。

## MySQL

好的面试官，我们继续。

### 1. 数据库事务的 ACID 特性

**结论式开场：**

ACID是事务的四个核心特性：**原子性、一致性、隔离性、持久性**，由MySQL的**undo log、redo log、锁机制**联合保证。

**主体：**

首先，**原子性**：事务中的所有操作要么全部成功，要么全部失败回滚。由`undo log`实现，回滚时恢复数据。然后，**一致性**：事务前后数据完整性约束不被破坏，比如账户转账总额不变。这是最终目标，由其他三个特性共同保证。其次，**隔离性**：多个事务并发执行时互不干扰。由**锁机制 + MVCC**实现。最后，**持久性**：事务提交后数据永久保存，即使宕机也不丢失。由`redo log`实现，宕机后重放恢复。

### 2. MySQL 存储引擎

**结论式开场：**

MySQL常用存储引擎：**InnoDB**（默认，支持事务、行锁、外键）、**MyISAM**（不支持事务，表锁，读多写少）、**Memory**（内存表，重启丢失）。

**主体：**

首先，**InnoDB**：最常用，支持ACID事务、行级锁、MVCC、外键约束。InnoDB的索引是**聚集索引**，数据和索引存储在一起。适用于绝大多数OLTP场景。然后，**MyISAM**：不支持事务和行锁，使用表锁，崩溃后恢复慢。优点是读性能高、占用空间小。适用于只读或读多写少的报表系统。其次，**Memory**：数据存在内存，读写极快，但重启数据丢失，支持表锁。适合临时表或缓存。**注意**：MySQL 8.0之后，系统表也强制使用InnoDB，MyISAM逐渐被淘汰。

### 3. 数据库的事务隔离级别

**结论式开场：**

SQL标准定义4种隔离级别，从低到高：**读未提交、读已提交、可重复读、串行化**。MySQL默认是**可重复读**。

**主体：**

首先，**读未提交**：一个事务可以读到另一个未提交事务的修改，会**脏读**，基本不用。然后，**读已提交**：只能读到已提交的修改，能解决脏读，但有**不可重复读**（同一事务两次查询结果不同）。Oracle默认级别。其次，**可重复读**：保证同一事务内多次查询结果一致，MySQL默认级别，解决了脏读和不可重复读，但可能出现**幻读**（InnoDB通过MVCC+间隙锁解决了）。最后，**串行化**：强制事务串行执行，读加共享锁，性能最低，最安全。

### 4. 索引的类型（种类）

**结论式开场：**

MySQL索引按功能分为：**主键索引、唯一索引、普通索引、全文索引、组合索引**；按存储结构分为**B+树索引和哈希索引**。

**主体：**

首先，**主键索引**：特殊的唯一索引，不允许NULL，每个表只能有一个。然后，**唯一索引**：索引列值必须唯一，允许一个NULL。**普通索引**：无唯一性约束，仅加速查询。**组合索引**：多列联合索引，需要遵循最左匹配原则。**全文索引**：用于全文检索（`MATCH AGAINST`），MyISAM和InnoDB 5.6+支持。其次，按存储引擎：InnoDB默认**B+树索引**；Memory引擎支持**哈希索引**，适合等值查询，但不支持范围查询。

### 5. 索引失效的情况有哪些

**结论式开场：**

索引失效的常见情况有**6种**：函数操作、隐式类型转换、不等于/IS NULL、OR连接、前导模糊查询、组合索引不满足最左匹配。

**主体：**

首先，**对索引列使用函数**：`WHERE DATE(create*time) = '2024-01-01'*`*，应该改成`create`*`time BETWEEN ...`。然后，**隐式类型转换**：字段是varchar，查询传int，比如`WHERE phone = 13800000000`，会导致全表扫描。其次，**使用`!=`、`<>`、`IS NULL`**：不等于和判空通常不走索引。**OR条件**：如果OR两边不是都有索引，会导致全表扫描。**前导模糊查询**：`LIKE '%abc'`不走索引，`LIKE 'abc%'`走。最后，**组合索引不满足最左匹配**：比如`(a,b,c)`索引，查询条件只用了b或c，不走索引。

### 6. MySQL 索引底层原理

**结论式开场：**

MySQL InnoDB索引底层采用**B+树**数据结构，叶子节点存储完整数据行（聚集索引）或主键值（二级索引），非叶子节点只存索引值用于快速定位。

**主体：**

首先，**B+树特点**：所有数据都在叶子节点，叶子节点之间由双向链表连接，支持范围扫描；非叶子节点只存索引值和子节点指针，高度通常为2~4层，每次查询只需2~4次磁盘I/O。然后，**查询过程**：从根节点二分查找，逐层向下定位到叶子节点，读取目标数据。其次，**为什么不用B树或红黑树**：B树叶子和非叶子都存数据，节点存储数据少，高度更高；红黑树是二叉树，高度过大，不适合磁盘存储。

### 7. 聚集索引与非聚集索引

**结论式开场：**

**聚集索引**：索引和数据存储在一起，叶子节点存完整行数据，每表只能一个（主键默认）；**非聚集索引**：索引和数据分离，叶子节点存主键值，需要回表查数据。

**主体：**

首先，**聚集索引**：InnoDB中主键就是聚集索引。如果没有主键，会用第一个唯一非空索引；都没有则隐式生成rowid。优点是查询速度快（一次I/O拿到数据），缺点是插入依赖顺序，主键最好是自增。然后，**非聚集索引**（二级索引）：叶子节点不存储完整行，只存储索引列的值+主键值。查询时先查二级索引拿到主键，再回聚集索引查完整行，这个过程叫**回表**。因此，尽量在查询中覆盖索引（索引中包含了要查询的所有字段），避免回表。

### 8. MySQL 回表查询

**结论式开场：**

回表是**通过非聚集索引查到主键值后，再到聚集索引查完整行数据的过程**，是InnoDB索引设计的代价。

**主体：**

首先，场景：表有`id`主键和`name`二级索引。查询`SELECT * FROM user WHERE name = '张三'`：先走name索引，拿到所有匹配的主键id，再一个个去聚集索引回表查完整行。然后，**回表次数**等于二级索引匹配的行数，如果匹配1000行，就回表1000次。因此，**避免回表的方法**：使用覆盖索引，比如`SELECT id, name FROM user WHERE name = '张三'`，name索引已经包含id和name，不需要回表。**Explain中Extra列显示"Using index"表示覆盖索引，显示"Using index condition"是ICP优化**。

### 9. MySQL 最左匹配原则

**结论式开场：**

最左匹配原则指**组合索引查询必须从索引最左边的列开始，跳跃列会导致后续列索引失效**。

**主体：**

首先，例子：组合索引`(a, b, c)`。查询`WHERE a = 1 AND b = 2 AND c = 3`：三个字段都用上了。查询`WHERE a = 1 AND c = 3`：只用到了a，c用不上，因为b被跳过了。然后，**范围查询**：`WHERE a = 1 AND b > 2 AND c = 3`：a和b用到了，c用不上，因为b是范围后c失去顺序。其次，**优化建议**：将高频等值查询的列放在左边，区分度高的列放左边。索引设计时考虑查询模式，`=`字段放前面，范围查询放后面。

### 10. count(*)、count(1)、count(字段)的区别？

**结论式开场：**

`count(*)*`*统计所有行数（包含NULL），`count(1)`效果等同`count(`*`)`，`count(字段)`统计该字段非NULL值的行数。性能上`count(*)`和`count(1)`没区别。

**主体：**

首先，`count(*)*`*：统计表中所有行的数量，包括NULL值，MySQL自动选择最小的二级索引来遍历（二级索引叶子节点小，I/O少），InnoDB不会扫描全表。然后，`count(1)`：扫描所有行，对每行计算常量1，效果和`count(`*`)`完全一样，优化器会改写为`count(*)*`*。其次，`count(字段)`：只统计该字段不为NULL的行数，如果字段有NOT NULL约束，效果等价于`count(`*`)`；否则会扫描全表或该索引。因此，**无脑用`count(`*`)`**，写起来短，性能也是最优的。

### 11. MySQL 优化方案

**结论式开场：**

MySQL优化从**三个层面**入手：**SQL与索引优化、表结构优化、架构层面优化（读写分离、分库分表）**。

**主体：**

首先，**SQL与索引优化**：通过慢查询日志找出慢SQL，使用Explain分析执行计划，关注type（至少range以上）、Extra（避免Using filesort/Using temporary），根据最左匹配原则建立合适的联合索引，避免索引失效。然后，**表结构优化**：字段尽量NOT NULL，小数据类型优先（int优于varchar），范式化减少冗余，大字段拆到子表。其次，**架构优化**：读多写少场景做主从复制+读写分离；单表数据量超过2000万考虑分库分表（ShardingSphere）；热点数据加缓存（Redis）。

### 12. SQL 优化方案

**结论式开场：**

SQL优化关注**减少扫描行数、避免回表、减少排序/分组开销**，核心是让索引发挥作用。

**主体：**

首先，**避免SELECT ***：只查需要的列，减少网络传输和回表概率。然后，**用Join代替子查询**：子查询会先执行结果集再与外层关联，Join优化器更好。其次，**分页优化**：`LIMIT 100000, 10`会扫描10万行后取10行，改成`WHERE id > 上次最大id LIMIT 10`（游标分页）或先子查询取主键再Join。**避免`ORDER BY RAND()`**：随机排序全表扫描。**批量操作**：INSERT/UPDATE/DELETE多条用批量语句，减少网络交互和锁竞争。**案例：**

之前一个报表接口用`SELECT * FROM orders WHERE status=1`扫了50万行，改成只查需要的5个字段，加联合索引`(status, create_time)`，从2秒降到30毫秒。

### 13. 如何设计数据库表

**结论式开场：**

表设计遵循**三范式**减少冗余，同时根据查询场景**适度反范式化**，关键点：**字段类型最小化、主键自增、合理加索引**。

**主体：**首先，**需求分析**：明确实体和关系，列出字段和依赖。字段类型原则：能用int不用varchar，能用varchar(50)不用varchar(255)，日期用datetime或timestamp。然后，**范式化**：第一范式（字段原子性）、第二范式（消除部分依赖）、第三范式（消除传递依赖），避免数据冗余和更新异常。其次，**反范式化**：高并发查询场景可冗余字段减少Join，比如订单表冗余商品名称，避免关联商品表。其他注意：每张表必须有主键（推荐自增bigint），预留扩展字段，添加合适的索引。

### 14. MySQL 都有哪些函数？

**结论式开场：**

MySQL函数分为**聚合函数、字符串函数、日期函数、数值函数、流程控制函数**五大类。

**主体：**

首先，**聚合函数**：`COUNT()`、`SUM()`、`AVG()`、`MAX()`、`MIN()`。然后，**字符串函数**：`CONCAT()`拼接、`SUBSTRING()`截取、`LENGTH()`长度、`REPLACE()`替换。**日期函数**：`NOW()`、`DATE*FORMAT()*`*格式化、`DATEDIFF()`日期差、`DATE`*`ADD()`增加。其次，**数值函数**：`ROUND()`四舍五入、`CEIL()`向上取整、`FLOOR()`向下取整。**流程控制函数**：`IF()`、`CASE WHEN`、`IFNULL()`。

**补充：**

注意：对索引列使用函数会导致索引失效，比如`WHERE DATE(create_time) = '2024-01-01'`，建议改成范围查询。

### 15. MySQL 三大日志文件

**结论式开场：**

MySQL三大日志是：**redo log**（重做日志，保证持久性）、**undo log**（回滚日志，保证原子性和MVCC）、**binlog**（归档日志，用于主从复制和数据恢复）。

**主体：**

首先，**redo log**：InnoDB特有，物理日志，记录“在某个数据页上做了什么修改”。写数据时先写redo log（WAL技术），再刷脏页，保证宕机后可以重放恢复，不会丢已提交数据。然后，**undo log**：逻辑日志，记录操作的逆操作。用于事务回滚和MVCC（提供读快照）。其次，**binlog**：Server层，逻辑日志，记录SQL语句的原始逻辑。用于主从复制和数据恢复。区别：redo log是循环写的，binlog是追加写的。

**补充：**

两阶段提交：事务提交时，先写redo log prepare，再写binlog，最后redo log commit，保证两个日志的一致性。

## Redis

好的面试官，我们继续。

### 1. Redis为什么快

**结论式开场：**

Redis快的原因有三个：**纯内存操作**、**单线程模型**（避免上下文切换和锁竞争）、**高效的数据结构**（如SDS、跳表、压缩列表）。

**主体：**

首先，**内存存储**：所有数据都在内存中，读写耗时是纳秒级，相比磁盘的毫秒级快了几个数量级。然后，**单线程模型**：避免了多线程的上下文切换、CPU竞争和锁开销。注意，Redis 6.0后的IO多线程只用于网络读写，命令执行依然是单线程。其次，**高效数据结构**：比如字符串用SDS（动态字符串，O(1)获取长度），有序集合用跳表（类似多级索引），哈希用渐进式rehash。因此，Redis是单线程但极快，瓶颈通常在网络IO。

### 2. Redis可以用来做什么

**结论式开场：**

Redis核心用途：**缓存**（最主要）、**分布式锁**、**计数器/限流**、**消息队列**（轻量级）、**排行榜**（有序集合）、**Session共享**、**布隆过滤器**。

**主体：**

首先，**缓存**：热点数据缓存，降低数据库压力，如商品详情、用户信息。然后，**分布式锁**：利用`SET NX`实现，Redisson提供自动续期。其次，**计数器**：微博点赞数、视频播放量，用`INCR`原子操作。**排行榜**：游戏积分榜、热搜榜，用ZSet的有序特性。**消息队列**：简单的发布订阅或List的LPUSH/RPOP实现轻量级队列。**Session共享**：分布式环境下多个节点共享用户会话。因此，Redis是后端工具箱里的瑞士军刀。

### 3. Redis的持久化机制

**结论式开场：**

Redis提供两种持久化：**RDB**（快照，定期保存全量数据，恢复快）、**AOF**（追加写命令，秒级丢失，可配置重写），生产环境通常**二者结合**。

**主体：**

首先，**RDB**：按配置（如`save 900 1`）或手动`BGSAVE`fork子进程，将内存数据快照写入dump.rdb文件。优点是文件小、恢复快；缺点是可能丢失最后一次快照后的数据。然后，**AOF**：记录每个写命令，追加到appendonly.aof文件。可以配置`appendfsync always/everysec/no`，推荐everysec（最多丢1秒数据）。AOF重写（`BGREWRITEAOF`）可以压缩文件。优点是持久性好；缺点文件大，恢复慢。因此，**混合持久化**（Redis 4.0）：RDB做全量，AOF做增量，兼顾恢复速度和数据安全。

### 4. Redis常用的数据类型

**结论式开场：**

Redis有**8种**数据类型，最常用5种：**String、Hash、List、Set、Sorted Set**，另有**Bitmaps、HyperLogLog、GEO**。

**主体：**

首先，**String**：最基础，可以是字符串、数字、JSON。典型用法：缓存对象、计数器、分布式锁。然后，**Hash**：键值对集合，适合存对象（如用户信息，可单独操作某个字段）。**List**：双向链表，支持LPUSH/RPOP，适合消息队列、最新消息列表。**Set**：无序去重，支持交并差运算，适合共同好友、标签。**Sorted Set**：带分数的有序集合，适合排行榜、延迟队列。其次，**Bitmaps**：位图，用于统计日活；**HyperLogLog**：基数统计，用于UV统计；**GEO**：地理位置，用于附近的人。

### 5. Redis的缓存雪崩、缓存穿透、缓存击穿（缓存三兄弟）

**结论式开场：**

**雪崩**：大量key同时过期或Redis宕机，请求全打到DB；**穿透**：查询不存在的数据，绕过缓存直接击穿DB；**击穿**：热点key过期瞬间，大量并发直接访问DB。

**主体：**

首先，**缓存雪崩**：解决方案：过期时间加随机偏移（如`3600 + random(600)`）；Redis高可用（主从+哨兵）；本地缓存加限流（Sentinel降级）。然后，**缓存穿透**：解决方案：布隆过滤器拦截不存在的key；缓存空对象（设置短过期时间）。其次，**缓存击穿**：解决方案：互斥锁（`SETNX`），只让一个线程去查DB，其他等待；热点数据永不过期，后台异步更新。因此，**三兄弟要区分清楚，解决方案不同**。**案例：**

之前遇到过零点秒杀，某个商品缓存过期瞬间，几千并发打挂DB。后来加了互斥锁，只有第一个请求去查DB，其他等待再读缓存，问题解决。

### 6. Redis的哨兵集群（Redis Sentinel）

**结论式开场：**

哨兵是Redis的**高可用解决方案**，主要功能：**监控**（检查主从健康）、**自动故障转移**（主节点挂了，提升从节点为主）、**配置中心**（通知客户端新主地址）。

**主体：**首先，**架构**：至少3个哨兵节点（奇数个，防止脑裂），哨兵之间互相通信，同时监控Redis主从。然后，**工作原理**：每个哨兵每秒ping主节点，如果多数哨兵（quorum）都认为主节点主观下线，就判定客观下线，开始选举leader执行故障转移。其次，**故障转移过程**：从节点中选一个（优先级高、数据新、runId小）执行`slaveof no one`成为新主，其他从节点指向新主，更新配置。因此，哨兵集群解决了单点故障，但不解决数据分片，海量数据需要Cluster。

### 7. Redis的分片集群（Redis Cluster）

**结论式开场：**

Redis Cluster是**分布式分片方案**，将数据自动分散到16384个槽位，每个节点负责一部分槽，支持水平扩展和自动故障转移。

**主体：**

首先，**核心机制**：所有key经过CRC16算法计算槽位（0~16383），客户端连接到任意节点，如果该节点不负责本次槽位，返回`MOVED`重定向。然后，**高可用**：每个主节点可有多个从节点，主节点挂了，从节点自动提升。集群至少需要3主3从（官方建议）。其次，**特点**：无中心架构，节点之间通过Gossip协议通信；不支持跨节点事务和多键操作（除非这些key在同一个槽位，可以用hash tag强制）。因此，Cluster适合海量数据场景，哨兵适合数据量适中、高可用场景。

### 8. 分布式锁用过吗？Redis分布式锁命令使用

**结论式开场：**

Redis分布式锁用`SET key value NX EX seconds`命令，核心是**原子性判断key不存在并设置过期时间**，释放时用Lua脚本校验holder。

**主体：**

首先，**加锁**：`SET lock*key unique*value NX PX 30000`，NX保证key不存在时才设置，PX设置30秒过期，unique_value用UUID或机器号+线程ID。然后，**释放锁**：用Lua脚本，先`GET`校验value是否是自己，是才`DEL`，防止误删别人的锁。脚本：`if redis.call("get",KEYS[1]) == ARGV[1] then return redis.call("del",KEYS[1]) else return 0 end`。其次，**问题**：锁超时业务没执行完，会被自动释放。解决方案用Redisson的看门狗自动续期。**案例：**

之前用Jedis实现锁，释放时没判断holder，结果A超时释放了B的锁，导致并发问题，后来改成Lua脚本校验。

### 9. Redis（或ElasticSearch）和MySQL如何保持数据一致性

**结论式开场：**

Redis和MySQL的一致性，常用**Cache Aside Pattern**（先更新DB，再删除缓存），结合**消息队列重试**保证最终一致性。

**主体：**首先，**标准流程**：写请求先更新MySQL，成功后删除Redis缓存；读请求先查Redis，miss则查MySQL并回写Redis。然后，**问题场景**：更新DB后删除缓存前，有读请求把旧数据写回缓存，导致脏数据。解决方案：**延时双删**：先删缓存，更新DB，sleep几百毫秒，再删一次。其次，**更可靠方案**：订阅MySQL binlog（Canal），解析后异步删除/更新Redis，用消息队列做重试。因此，**高并发下做到强一致不可能**，只能根据业务容忍度选择最终一致或加分布式锁。

### 10. Redisson是什么，怎么用

**结论式开场：**

Redisson是**Redis的Java客户端**，封装了分布式锁、队列、信号灯等高级功能，相比Jedis更面向对象，像使用Java集合一样使用Redis。

**主体：**

首先，**使用方式**：引入依赖，配置`RedissonClient`，然后通过`getLock(key)`获取`RLock`对象，调用`lock()`和`unlock()`。示例：

```
RLock lock = redissonClient.getLock("myLock");
lock.lock(10, TimeUnit.SECONDS);
try {
    // 业务逻辑
} finally {
    lock.unlock();
}
```

然后，**核心优势**：看门狗自动续期（默认每10秒续到30秒），解决锁超时问题；支持可重入、公平锁、读写锁、红锁（RedLock）。其次，**其他功能**：分布式集合（RMap、RList）、分布式队列（RBlockingQueue）、信号量（RSemaphore）。

### 11. Redisson看门狗机制的原理

**结论式开场：**

看门狗是**后台定时任务**，当锁未主动释放且业务未完成时，自动续期锁的过期时间，默认每`lockTimeout/3`秒续期一次，默认超时30秒。

**主体：**

首先，**触发条件**：调用`lock()`时不传入超时时间，或传入负数时，看门狗生效。Redisson会设置锁过期时间为30秒（可配置看门狗超时）。然后，**工作流程**：客户端成功获取锁后，启动一个后台线程（看门狗），每隔10秒（`30秒/3`）检查当前线程是否还持有锁，如果是，执行Lua脚本`expire`命令将锁续期到30秒。其次，**释放时机**：调用`unlock()`时，看门狗线程被中断并停止续期。因此，**看门狗保证业务没执行完，锁不会自动释放**，避免了锁超时误释放的经典问题。

**补充：**

如果手动传入锁时间（如`lock(5, TimeUnit.SECONDS)`），看门狗不生效，锁在5秒后自动释放，可能造成业务未完成锁被抢走。
