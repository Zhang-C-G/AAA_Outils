# 全局私人偏好：自动保存与保存按钮偏好

最近同步：`2026-05-20`

## 1. 定位

本文件记录持续编辑型模块与个性化设置类面板在保存链路上的全局硬规则。

## 2. 具体规则

### 2.1 自动保存优先于手动保存按钮

- 对持续编辑型模块，优先自动保存
- 手动保存按钮不是默认必选项
- 对个性化设置类面板，自动保存不是推荐项，而是默认硬规则
- 对这类面板，修改后默认即时生效，不走“先预览、再保存、再应用”的通用设置页逻辑

### 2.2 保留按钮不是目的，保存闭环才是目的

- 如果模块已经有稳定自动保存链路，就不优先再保留显式保存按钮
- 是否保留保存按钮，取决于真实闭环是否稳定，而不是取决于习惯性堆按钮
- 个性化设置类面板默认禁止出现“保存”“应用”“预览”按钮
- 只有高风险、不可逆、跨模块批量变更，才允许例外保留一次确认入口
- 对“正文工作区”这类持续编辑面，允许存在一个低优先级的手动“保存”按钮，但它只能做两件事：
  - 立即触发当前已经存在的保存链路
  - 给用户提供心理确认或主动落盘入口
- 这种例外按钮不允许改变默认交互口径：
  - 不能替代自动保存
  - 不能引入第二套“编辑完成后再保存”的工作模式
  - 不能把普通输入、失焦、结构性修改从自动保存链路里拿掉
- 出现例外时，必须在模块文档中写明：
  - 为什么不能即时生效
  - 为什么不能自动保存
  - 用户按下确认按钮后到底确认了什么

### 2.3 自动保存必须带兜底

- 自动保存不是“表面自动”，而是要有刷新、切换、异常时的可靠兜底
- 如果没有这些兜底，就不应轻易删掉保存入口
- 即时生效类面板也必须有真实写入、刷新恢复、重启恢复的闭环验证

### 2.4 正文可视编辑也算真实编辑

- 如果模块提供 `最终版本`、预览态正文、富文本态正文这类“可直接改内容”的面，它不属于只读展示，应按真实编辑面接入自动保存
- 这类编辑面中的结构性修改，例如选区改色、列表退出、视图内直接删改内容，不能只在视觉层生效，必须进入真实保存链路
- 如果某类修改不是普通键盘输入触发，也应补失焦保存、静默保存或动作后立即入队等兜底，不允许把用户改动留在只会暂时显示的 DOM 里

## 3. 执行要求

- 第一阶段只要出现个性化设置类面板，就必须直接按本规则落 UI 壳层
- 第二阶段必须验证：
  - 当前界面即时生效
  - 后端或本地配置真实写入
  - 刷新后状态恢复
  - 重启后状态恢复
- 不允许先按通用组件习惯放入保存式交互，再留到后续再删
