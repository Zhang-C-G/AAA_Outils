# AI 开发总指引
最近同步：`2026-05-14`

## 1. 定位

这份文档是任何开发阶段开始前的强制入口。  
它回答的不是“代码怎么写”，而是：

- 先读什么
- 先做什么
- 什么情况下不能直接开写
- 第一阶段和第二阶段分别该产出什么

## 2. 强制入口规则

- 每次开始任何实际任务前，必须先读 `docs/USER_DOC_SYSTEM_GUIDE.md`
- 每次开始新的开发阶段前，必须先读本文件
- 如涉及具体业务模块，还必须继续读对应 `docs/modules/*.md`
- 如涉及悬浮窗、保护态、截图问答链路，还必须继续读 `docs/extension/OVERLAY_STAGE2_GUIDE.md`
- 如本轮涉及新建文档、大改文档或补文档体系规则，还必须继续读 `docs/extension/文档低耦合与拆分规则.md`
- 如本轮需求与已有模块结构高度相似、只是换字段或换链路，还必须继续读 `docs/extension/模块库总索引.md`
- 如进入第一阶段，也必须读取 `docs/extension/全局私人偏好文档.md`，并按需进入与 UI 结构、交互骨架相关的偏好子文档
- 如进入第二阶段，还必须继续读取与行为闭环、持久化、运行时生效相关的偏好子文档
- 如进入第二阶段的是真实闭环开发，还应先读 `docs/incidents/STAGE2_RISK_KB.md`

这里的“开发阶段”包括：
- 新模块第一阶段
- 新模块第二阶段
- 老模块新增能力
- bug 修复
- 只补文档
- 新配置项接入

补充理解：

- `回归修复` 不再单列为独立任务类型，统一并入 `bug 修复`
- 一旦已在判断树中确认属于第一阶段或第二阶段，就继续回到本文件执行对应阶段规则

## 3. 总原则

### 3.1 核心优先
- 先定义模块的核心主功能，再谈体验优化
- 任何样式、交互、微调都不能以破坏核心功能为代价

### 3.2 通用兼容优先
- 不把核心能力绑定在单一网站、单一软件或单一录屏工具的定向兼容上
- 默认按通用环境设计

### 3.3 四层同步
凡是新增开关、下拉、按钮、输入、状态位，都要同步检查四层：

1. 前端显示与回填
2. 后端读取与保存
3. 本地默认值与持久化
4. 运行时真实生效

缺任意一层，都不算完成。

### 3.4 文档同步
- 改模块：更新 `docs/modules/*.md`
- 改跨模块共用规则：更新 `docs/shared/*.md`
- 改架构或系统行为：更新 `docs/components/*.md` 或相关总文档
- 改阶段结论或接手状态：更新 `docs/AI_HANDOFF.md`

### 3.5 文档低耦合
- 总入口文档不展开长细则
- 一份文档默认只承担一种主职责
- 同时涉及全局规则、模块说明、故障记录时，必须按层拆开
- 如新增规则已经具备跨模块复用价值，应优先抽为独立规则文档，而不是继续塞回单模块文档

### 3.6 模块库优先
- 对于已经出现过多次的稳定结构，优先复用模块母版，而不是重新搭壳
- 复用时先选结构母版，再挂交互和闭环能力
- 母版只复用稳定部分，不把旧模块整块复制成新模块

## 4. 统一采用两阶段开发法

所有模块默认都按两阶段处理：

1. 第一阶段：结构定义
2. 第二阶段：真实闭环

### 4.1 第一阶段：界面与结构阶段

第一阶段的目标是先把模块的结构、入口、区块、占位搭起来。  
重点是“看得见、进得去、结构稳定”，不是完整业务闭环。

第一阶段虽然以 UI 结构为主，但不能脱离全局偏好单独设计。  
否则第二阶段很容易因为偏好冲突而返工整个界面。

第一阶段必须完成：
1. 模块名称、定位、核心主功能说明
2. 模块入口、标签页或导航入口
3. 页面布局、区块划分、标题层级
4. 关键控件占位
5. 默认态、空态、说明态
6. 与现有模块的关系
7. 第二阶段待补项

第一阶段文档必须强制补齐：
1. 文档定位
2. 输入文档 / 输出文档
3. 区块状态表
4. 本阶段不做什么
5. 阶段切换条件
6. 第一阶段完成标准

第一阶段必须读取并应用的偏好类型：
1. UI 结构类偏好
2. 控件样式类偏好
3. 交互骨架类偏好

例如：
- 栏目框如何进入编辑态
- 按钮是否允许保留保存按钮
- 说明条是否使用斜杠背景
- 删除确认是否使用自定义弹窗
- 标签页、列表、说明区是否已有固定风格

第一阶段不要求把所有行为闭环类偏好全部实现，但不能先做出与偏好冲突的结构壳子。

第一阶段明确不要求全部完成的内容：
- 真实后端保存
- 真实持久化
- 真实运行时生效
- 完整异常链路
- 完整热键 / 悬浮窗 / 保护链路

第一阶段完成标准：
- 页面结构已稳定
- 用户已经能看懂这个模块将来做什么
- 第二阶段无需重做整体布局
- 本阶段未做事项已写清楚

### 4.2 第一阶段进入第二阶段的判定

允许进入第二阶段的条件：
- UI 结构稳定
- 入口和区块边界稳定
- 字段集合基本稳定
- 第一阶段文档已补齐
- 阶段前 git 已执行

禁止进入第二阶段的情况：
- 页面结构还在频繁推翻
- 区块职责还不清晰
- 关键字段尚未定名
- 用户入口仍不明确

### 4.3 第二阶段：真实能力开发阶段

第二阶段的目标，是把模块从“有壳”变成“可用”。  
这一步不是想到什么就直接接代码，而是先定义能力，再实现。

第二阶段首次真实开发前的顺序必须是：
1. 先写标准能力说明文档
2. 再读取全局私人偏好总入口
3. 再读取与本次能力相关的行为闭环类、持久化类、运行时类偏好子文档
4. 再读取第二阶段风险知识库，确认是否命中历史高频失败模式
5. 融合形成最终能力说明
6. 再按最终能力说明开始实现

执行原则：
`标准能力说明 -> 偏好映射 -> 风险检查 -> 最终能力说明 -> 实现 -> 测试 -> 记录`

新增执行规则：
- 每次当前任务完成后，Codex 可以提出与当前任务强相关的优化建议
- 对于 Codex 自己提出的优化建议，不能直接默认扩展为新任务，必须先做一次自评
- 只有同时满足以下条件，才允许直接继续落What?地该优化：
  1. 与当前任务目标强相关
  2. 风险低且影响范围可控
  3. 不改变当前任务的产品目标或边界
  4. 不需要用户再次做新的产品方向决策
  5. 可以在当前轮完成实现、测试与记录
- 如不满足上述条件，则只保留为建议，写明原因，不自动扩展执行
- 后续每次阶段汇报、过程汇报、最终汇报，都必须显式说明关键执行状态
- 回复中不再强制要求写“当前轮次 / 第几轮”；如用户明确不需要，则不得机械附加该表述

第二阶段文档必须强制补齐：
1. 文档定位
2. 输入文档 / 输出文档
3. 用户操作链路
4. 数据链路
5. 运行时生效链路
6. 异常与边界
7. 偏好约束映射
8. 测试清单
9. 本阶段完成标准
10. 恢复锚点

第二阶段必须完成：
1. 前端显示、交互、回填
2. 后端读取、保存、聚合返回
3. 本地默认值、持久化、重启恢复
4. 运行时真实生效
5. 异常处理与日志
6. 测试与回归验证
7. 文档落档

第二阶段完成标准：
- 用户操作链路闭环
- 数据链路闭环
- 运行时链路闭环
- 偏好约束已应用
- 测试执行并通过

## 5. 新模块开发顺序

1. 先写模块文档草稿
2. 先做第一阶段：界面与结构
3. 第一阶段完成后 git
4. 再写第二阶段能力说明
5. 读偏好并形成最终能力说明
6. 再做真实保存、持久化、运行时链路
7. 每次改动测试通过后记入变更文档
8. 满 3 次完成改动后执行 git checkpoint

## 6. 新配置项接入规则

凡是新增开关、下拉、输入、按钮、状态位，都按下面检查：

1. 前端默认值
2. 前端回填
3. 前端保存请求
4. 后端状态聚合
5. 后端保存逻辑
6. 本地默认值
7. 本地读取逻辑
8. 运行时应用逻辑
9. 模块文档说明

排查“看起来保存了，但重开又丢了”时，必须分清三层：
1. 前端是否真的发出了有效保存数据
2. 后端是否真的写入本地存储
3. 重新加载时是否真的从本地读回

## 7. 测试原则

- 每次改动只有在测试通过后，才算完成
- 页面内刷新与浏览器原生刷新要分开验证
- 自动保存模块要验证草稿恢复链路
- 持久化模块要验证重启后读取一致
- 高风险模块要做专项回归

## 8. 提交与归档

每次重要提交说明至少包含：
1. 这次实现了什么
2. 这次没有实现什么
3. 当前可回滚锚点是什么
4. 下一步从哪里继续最安全

配套文档：
- `docs/AI_HANDOFF.md`
- `docs/CHANGE_CHECKPOINT_RULE.md`
- `docs/CHANGE_ACTIVITY_LOG.md`
- `docs/modules/changelog/*.md`

## 8.1 回答格式补充约束

以后凡是实际开发过程中的对话回复，不只要说明做了什么，还必须带上关键状态信息。

目标不是把回答写长，而是让用户能快速判断：

1. 该做的步骤有没有做
2. 哪些步骤已经完成
3. 哪些步骤还没完成
4. 当前卡在哪一层

最低要求如下：

1. 已做事项
2. 未做事项
3. 文档状态
4. 测试状态
5. git 状态

其中：

- `git 状态` 必须按“本轮是否执行”汇报，不能只写笼统结果
- `git 状态` 负责统一说明：本地提交、当前循环进度、是否已 push、推送到哪里、计数是否重置
- 显性回答默认以“短总结 + 关键状态”表达，不展开成长篇过程复述
- 只要能支持用户快速判断是否已按流程执行，就不要继续堆细节

## 9. Git 检查点强制规则

- 正式进入第一阶段前，必须先创建 git 检查点
- 正式进入第二阶段前，必须再次创建 git 检查点
- 每 3 次完成且测试通过的改动，必须执行 checkpoint
- 默认本地 commit 后直推 `origin/main`

## 10. 统一开工顺序

以后凡是进入任何实际开发、扩展、修复、回归或配置接入，默认先按下面顺序判断和读取：

1. 先读 `docs/USER_DOC_SYSTEM_GUIDE.md`
   - 先确认这是不是实际任务
   - 先确认有没有命中具体模块
   - 先确认任务类型
   - 一旦已判断出阶段，再回到本文件执行阶段规则
2. 再读 `docs/extension/AI_DEVELOPMENT_PLAYBOOK.md`
   - 先确认当前该执行哪些阶段规则和强制约束
3. 再判断是否涉及具体业务模块
   - 读取对应模块主文档 `docs/modules/*.md`
   - 读取对应模块修改过程文档 `docs/modules/changelog/*.md`
4. 再判断是否涉及第一阶段或第二阶段约束
   - 第一阶段：优先确认结构、入口、区块、占位、阶段边界
   - 第二阶段：优先确认标准能力说明、真实闭环、运行时生效、测试与恢复锚点
5. 再判断是否涉及悬浮窗、保护态、截图问答链路
   - 命中时必须继续读 `docs/extension/OVERLAY_STAGE2_GUIDE.md`
6. 再判断是否涉及 UI、交互、结构、保存方式或文案
   - 读取 `docs/extension/全局私人偏好文档.md`
   - 读取 `docs/extension/global_preferences/00_通用偏好结论.md`
   - 再按需读取对应偏好子文档
7. 再判断是否涉及跨模块共用规则
   - 命中时继续读取 `docs/shared/*.md`、`docs/components/*.md`、`docs/config/*.md` 中的对应文档
8. 开发完成后再对照 `docs/UPDATE_CHECKLIST.md` 收尾

补充约束：
- 不允许跳过“阶段判断”直接开改。
- 不允许只看模块主文档，不看模块修改过程文档。
- 不允许只看私人偏好总结，不判断当前属于第一阶段还是第二阶段。
- 最终交付说明必须明确列出本轮更新过的文档。

## 11. 每次回答的显式交付格式

以后每次面向用户的阶段性说明或最终交付，默认都要显式交代下面这些状态，不允许只说“改好了”：

推荐结构：

1. 已做事项
2. 未做事项
3. 文档状态
4. 测试状态
5. git 状态

写法要求：

- 每一项都尽量短
- 优先写结论，不先堆过程
- 能一眼判断“做没做、做到了哪一步、还有什么没做”
- 不为了显得完整而重复已经说过的话
- 不允许只写口号式结论，例如“已处理完成”“已同步”而没有最小必要说明

判定目标：

- 用户看完后，应能直接判断这次是否已经按要求完成：
  - 文档同步
  - 测试执行
  - git / push / 计数状态
  - 未完成项说明

补充要求：
- 如果本轮没有做 git，也必须显式说“未做”以及原因。
- 如果本轮没有补文档，也必须显式说“未补”以及原因。
- 如果本轮没有跑测试，也必须显式说“未测”以及原因。
- 如果某一项已经大体完成，只保留够判断的摘要，不再继续展开冗长描述。
