# 文档低耦合与拆分规则

最近同步：`2026-05-09`

## 1. 文档定位

这份文档用于约束整个项目的文档结构，目标不是把内容写多，而是把职责写清。  
它解决的是三个问题：

1. 防止一个文档承担过多职责，后续难改
2. 防止不同层级文档互相重复、互相缠绕
3. 让 AI 和人都能快速判断“这条内容该写到哪里”

## 2. 硬规则

### 2.1 单文档单职责

- 一份文档默认只承担一种主职责
- 不能把“模块功能说明 + 偏好规则 + bug 排障 + 改动流水”长期堆在同一份文档里
- 如果一份文档已经同时承担多种职责，必须拆分

### 2.2 总入口不展开长细则

- 总入口类文档只负责：
  - 给入口
  - 给读取顺序
  - 给分层说明
  - 给索引
- 总入口不负责展开长篇实现细则
- 细则必须下沉到对应子文档

### 2.3 阶段文档不混写

- 第一阶段文档负责结构、入口、布局、区块、占位
- 第二阶段文档负责行为闭环、数据链路、持久化、运行时生效、异常边界
- 不能把第二阶段的真实闭环细节提前塞进第一阶段主文档里，导致文档目标失焦
- 允许在第一阶段文档里写“第二阶段待补项”，但不允许直接替代第二阶段能力说明

### 2.4 全局规则与模块规则分层

- 全局共识写入全局文档
- 只对某一个模块生效的内容写入对应模块文档
- 某个模块触发出来、但未来会复用到多个模块的规则，应抽出为全局规则文档，再由模块文档引用

### 2.5 记录文档与说明文档分层

- 模块主文档：讲这个模块是什么、怎么做
- 模块修改过程文档：讲这个模块改过什么
- incident 文档：讲某次真实故障是什么
- 风险知识库：讲哪些风险可复用为预防知识
- 这四类文档不能互相替代

### 2.6 不重复写同一套细则

- 同一条规则只允许有一个主落点
- 其他文档如果需要提到，只写：
  - 简述
  - 链接
  - 适用范围
- 不允许在多个文档里维护多份几乎相同的长规则正文

## 3. 何时必须拆分

满足任一条，就应考虑拆分，而不是继续往原文档堆：

1. 一份文档已经同时承担 3 类以上职责
2. 同一份文档里同时长期维护“阶段定义 + 真实闭环 + 排障记录”
3. 每次改一个点都要顺手改同文档里很多不相干章节
4. 新人或 AI 读完后，仍然判断不出“下一步该看哪份文档”
5. 某段规则已经明显可复用于多个模块
6. 某一章节已经独立成主题，后续会被高频单独修改

## 4. 推荐拆分方式

### 4.1 按层拆

- 总入口层
- 模块层
- 第一阶段层
- 第二阶段层
- 风险 / incident 层
- 流程治理层

### 4.2 按主题拆

- 交互偏好
- 控件偏好
- 目录与正文工作区偏好
- 表格与筛选器偏好
- 悬浮窗专项规则

### 4.3 按变化频率拆

- 高频改动内容单独成文
- 低频稳定共识保留在总规则中
- 避免把高频改动内容长期埋在稳定总纲里

## 5. 新增内容时的落点判断

遇到一条新内容时，按这个顺序判断：

1. 这是全局规则，还是单模块规则
2. 这是第一阶段结构问题，还是第二阶段闭环问题
3. 这是长期共识，还是单次故障
4. 这是说明性文档，还是过程记录文档
5. 当前是否已有合适子文档可承接

判断完后再写，不能先堆进去再说。

## 7. 当前执行结论

1. 以后不允许把过多新规则持续堆回单一总文档
2. 新规则优先判断层级，再决定是否新建子文档
3. 总入口类文档只补索引，不补长细则
4. 模块扩展时，如某条规则已具备跨模块复用价值，应及时抽离为全局规则
5. 实际任务的总判断入口先以 `docs/USER_DOC_SYSTEM_GUIDE.md` 为准，再回到各子规则文档
